A 功能定义

原草图强调五步业务路径：了解 SIG 运营 → SIG 上线 → 仓开源 → 运营资源申请 → 计划与目标管理。【输入：草图登录页及侧栏】低保真将其实现为四个能力页签：运营总览、资源申请、申请与审批、资源配置；上线和仓开源成为资源申请的业务场景。【输入：低保真页签、申请向导】这两种表达应同时存在：五步路径帮助理解业务，四个页签负责实际操作。【设计推断】

B 使用场景

  1. 新 SIG 的 Maintainer 想宣告成立：选所属 SIG，填写背景和目标，选择宣传方式、媒体、渠道与排期，上传对应素材并提交。【输入：草图 SIG 上线；低保真申请向导】
  2. 运营审核员处理申请：在“待我处理”找到单据，核对素材与排期，审批后推进营销审核和排期确认。【输入：低保真审批链】
  3. 运营管理员做季度复盘：切换全部 SIG，查看目标、计划、推广记录和度量摘要，定位需要跟进的 SIG。【输入：低保真运营总览】
  4. 运营操作员维护资源：按宣传方式与媒体配置渠道、反馈指标和可申请范围，提交变更后由审核角色生效。【输入：低保真资源配置】

C 目标用户

用户常见任务所需界面支持
SIG Maintainer / Committer发起、跟踪本 SIG 推广，查看目标本 SIG 上下文、清晰的申请阶段、申请状态
运营管理员跨 SIG 看全局、代提申请全部 SIG 切换、汇总与下钻
SIG 运营审核员 / 营销审核员审核申请与排期待我处理、责任人、审核意见
SIG 运营操作员执行发布、填写反馈、维护资源执行清单、资源配置、状态反馈

使用频率、具体组织人数与多角色兼任规则【待确认】。

D 核心流程

申请者：选择 SIG 与基本信息 → 选择宣传方式、媒体、渠道与排期 → 上传素材/奖品材料 → 提交 → 在申请与审批中跟进 → 查看发布位置和反馈 → 在总览关联目标、复盘成果。【输入：低保真】

协作者：SIG 评审 → 运营审批 → 营销审批 → 排期确认 → 运营执行 → 推广反馈 → 办结。【输入：低保真 v2.12 的当前交互与步骤条】审批人回避提交者、部分阶段可能调整排期；具体撤回和重提规则在源文件版本备注中有冲突，【待业务确认】，优化稿未改状态机。

E 设计机会点

优先级机会落地条件
P0 · 前端可做总览首屏提供清晰的申请、跟进动作沿用现有页签和权限判断
P0 · 前端可做五步业务路径与四页能力入口建立映射路径作为引导，避免增加重复业务页面
P0 · 前端可做申请首步的长说明折叠保留完整规则可查看
P1 · 需产品确认各角色待办数、逾期数、审批时长等工作指标确认口径与后端字段
P1 · 需后端配合资源申请与目标效果的可追溯关联接口与数据口径对齐
P2 · 需产品确认提交前预估审核时长和冲突提醒有真实时效/排期规则后再做

F 竞品参照

GitHub 将社区公告、讨论与项目参与放在同一协作空间，官方说明可作为内容发布与后续互动的参照。GitHub 仓库流量和 GitLab 贡献分析分别展示传播访问与实际协作两类指标，提示本看板应区分“触达”与“参与”。【外部】这只是功能模式参照，不代表其具有本项目的多级资源审批链。

G 设计注意事项

  • 不把原草图的五个阶段误实现成五套重复表单；沿用低保真的统一申请能力。【输入 + 设计推断】
  • 不把示例数值当真实业务指标。示例时间、人物、邮箱、目标值仅用于演示。【输入：两个 HTML】
  • 审批状态与当前阶段是两个维度；“已通过”之后仍可能有排期、执行与反馈。【输入：低保真】
  • 资源档期展示已排情况，冲突由审核员判断；不要在 UI 上推断系统有固定容量限制。【输入：低保真 v2.12】
  • 空、加载、错误、禁用状态要与合法的零值区分；真实接入时需逐页补全。【待确认：后端契约未提供】

H 商业价值与优先级

P0 是降低首次进入的理解成本和发起申请的路径成本；P1 是提高处理效率和复盘可信度；P2 是预测与自动提醒。当前没有量化基线，因此不写节省时间或增长比例。建议上线后衡量：首访发起率、申请提交完成率、各审批阶段耗时、排期调整率、推广办结率和目标关联率。【推断·待确认】
